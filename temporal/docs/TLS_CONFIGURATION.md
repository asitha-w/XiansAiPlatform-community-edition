# Temporal TLS/mTLS Configuration

This document explains how TLS and mTLS are configured for Temporal in this deployment.

## Overview

**Status:** ✅ **Enabled** - Full mTLS for all connections

**What's Protected:**
- ✅ Frontend service (SDK, tctl, UI → Temporal)
- ✅ Internode communication (Temporal services talking to each other)
- ✅ Client authentication (mutual TLS - both sides verify certificates)

## Configuration Method

Unlike `temporalio/auto-setup`, the production `temporalio/server` image requires **config file** for TLS, not just environment variables.

### Configuration File: `temporal/config/docker.yaml`

```yaml
global:
  tls:
    # Frontend service TLS (client connections)
    frontend:
      server:
        certFile: /etc/temporal/certs/temporal.crt
        keyFile: /etc/temporal/certs/temporal.key
        clientCaFiles:
          - /etc/temporal/certs/ca.crt
        requireClientAuth: true  # ← This enables mTLS
      client:
        rootCaFiles:
          - /etc/temporal/certs/ca.crt
    
    # Internode TLS (service-to-service)
    internode:
      server:
        certFile: /etc/temporal/certs/temporal.crt
        keyFile: /etc/temporal/certs/temporal.key
        clientCaFiles:
          - /etc/temporal/certs/ca.crt
        requireClientAuth: true
      client:
        rootCaFiles:
          - /etc/temporal/certs/ca.crt
```

## Certificates

All certificates are auto-generated by `scripts/create-secrets.sh` and stored in `temporal/certs/`:

| File | Purpose | Details |
|------|---------|---------|
| `ca.crt` | Root CA | Signs all certificates |
| `temporal.crt` | Server certificate | SAN: `temporal`, `localhost` |
| `temporal.key` | Server private key | For Temporal server |
| `temporal-ui.crt` | Client certificate | CN: `temporal-ui` |
| `temporal-ui.key` | Client private key | For Temporal UI |

## Docker Compose Integration

### Temporal Server

```yaml
temporal:
  volumes:
    - ./certs:/etc/temporal/certs:ro
    - ./config/docker.yaml:/etc/temporal/config/docker.yaml:ro
```

### Temporal UI (Client)

```yaml
temporal-ui:
  environment:
    - TEMPORAL_TLS_CA_CERT=/etc/temporal/certs/ca.crt
    - TEMPORAL_TLS_CERT=/etc/temporal/certs/temporal-ui.crt
    - TEMPORAL_TLS_KEY=/etc/temporal/certs/temporal-ui.key
  volumes:
    - ./certs:/etc/temporal/certs:ro
```

### Init Containers (tctl)

```yaml
temporal-namespace-setup:
  command:
    - tctl
    - --address temporal:7233
    - --tls
    - --tls-cert-path /etc/temporal/certs/temporal-ui.crt
    - --tls-key-path /etc/temporal/certs/temporal-ui.key
    - --tls-ca-path /etc/temporal/certs/ca.crt
  volumes:
    - ./certs:/etc/temporal/certs:ro
```

## Verification

### 1. Check TLS is Enforced

**Without TLS (should fail):**
```bash
docker exec temporal tctl --address temporal:7233 cluster health
# Error: connection refused or TLS handshake failure
```

**With TLS (should succeed):**
```bash
docker exec temporal tctl \
  --address temporal:7233 \
  --tls \
  --tls-cert-path /etc/temporal/certs/temporal-ui.crt \
  --tls-key-path /etc/temporal/certs/temporal-ui.key \
  --tls-ca-path /etc/temporal/certs/ca.crt \
  cluster health
# Output: temporal.api.workflowservice.v1.WorkflowService: SERVING
```

### 2. Check Server Logs

```bash
docker logs temporal 2>&1 | grep -i tls
```

Look for:
- ✅ `"TLS enabled"` or similar messages
- ✅ `"Loading TLS certificates"`
- ✅ `"requireClientAuth": true`

### 3. Test Certificate Validation

**With valid certificate:**
```bash
# Using temporal-ui certificate (should work)
docker exec temporal tctl \
  --tls \
  --tls-cert-path /etc/temporal/certs/temporal-ui.crt \
  --tls-key-path /etc/temporal/certs/temporal-ui.key \
  --tls-ca-path /etc/temporal/certs/ca.crt \
  --address temporal:7233 namespace list
```

**Without certificate (should fail):**
```bash
# No client cert (should fail with mTLS enabled)
docker exec temporal tctl \
  --tls \
  --tls-ca-path /etc/temporal/certs/ca.crt \
  --address temporal:7233 namespace list
# Error: certificate required
```

## Troubleshooting

### Issue: "first record does not look like a TLS handshake"

**Cause:** Temporal server not actually loading TLS config

**Fix:**
1. Verify `docker.yaml` is mounted: `docker exec temporal ls -la /etc/temporal/config/`
2. Check file permissions: Should be `644` (readable by all)
3. Verify certificates exist: `docker exec temporal ls -la /etc/temporal/certs/`

### Issue: "x509: certificate signed by unknown authority"

**Cause:** Client doesn't trust the CA

**Fix:**
1. Ensure `--tls-ca-path` points to correct CA
2. Verify CA file is readable: `docker exec temporal cat /etc/temporal/certs/ca.crt`

### Issue: "tls: bad certificate"

**Cause:** Server rejects client certificate

**Fix:**
1. Ensure client cert is signed by the same CA
2. Verify certificate files: `openssl x509 -in temporal/certs/temporal-ui.crt -text -noout`
3. Check CN matches: Should be `temporal-ui`

### Issue: Namespace setup fails with TLS error

**Cause:** `temporal-namespace-setup` doesn't have certificates mounted

**Fix:**
```yaml
temporal-namespace-setup:
  volumes:
    - ./certs:/etc/temporal/certs:ro  # ← Must be present
```

## Architecture Decisions

### Why Config File Instead of Environment Variables?

- `temporalio/auto-setup` supports simple env vars (`TEMPORAL_TLS_CERT`, etc.)
- `temporalio/server` (production image) **requires** config file for full TLS control
- Config file provides granular control over frontend vs. internode TLS

### Why Same Certificate for Server and Internode?

- Simplifies certificate management
- Single certificate with proper SANs works for both use cases
- Production deployments often use separate certs, but for this setup, shared cert is sufficient

### Why Separate Client Certificate for UI?

- Follows mTLS best practice: server cert ≠ client cert
- Allows per-client access control (could add more clients with different certs)
- Client cert has CN (`temporal-ui`), server cert has SANs (`temporal`, `localhost`)

## Key Takeaways

1. ✅ **Config file is mandatory** for `temporalio/server` TLS
2. ✅ **mTLS is enabled** (`requireClientAuth: true`)
3. ✅ **All clients need certificates** (UI, tctl, SDKs)
4. ✅ **Certificates are auto-generated** during `./start-all.sh`
5. ✅ **Hostname-based certificates** for proper TLS validation
