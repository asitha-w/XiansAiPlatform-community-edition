# XiansAI Server mTLS and SDK Certificates

## Overview

The XiansAI server acts as both an HTTPS server and a Temporal client, requiring dual-purpose certificates for secure communication. This document details the server's mTLS configuration and SDK certificate management.

## Certificate Architecture

### Dual-Purpose Certificates

All service certificates in the XiansAI platform are **dual-purpose**, supporting both:
- **Server Authentication** (`serverAuth`): For accepting HTTPS connections
- **Client Authentication** (`clientAuth`): For connecting to Temporal with mTLS

### Server Certificate Structure

The XiansAI server uses two main certificates:

1. **HTTPS Server Certificate** (`server.pfx`)
   - **Purpose**: HTTPS server authentication
   - **Subject**: `CN=xiansai-server`
   - **Usage**: Web API endpoints, UI serving
   - **Extended Key Usage**: `serverAuth, clientAuth`

2. **Temporal SDK Client Certificate** (`sdk-client.crt`)
   - **Purpose**: Temporal client authentication with mTLS
   - **Subject**: `CN=XiansAi, OU=<user_id>, O=<tenant_id>`
   - **Usage**: Connecting to Temporal server
   - **Extended Key Usage**: `serverAuth, clientAuth`

## Environment Configuration

### Server Environment Variables

The server's `.env.local` file contains the following certificate-related variables:

```bash
# HTTPS Server Certificate (PFX format)
Certificates__AppServerPfxBase64=<base64-encoded-pfx>

# Temporal mTLS Configuration
Temporal__ServerName=temporal
Temporal__CertificateBase64=<base64-encoded-client-cert>
Temporal__PrivateKeyBase64=<base64-encoded-client-key>

# CA Certificate (for trusting Temporal server)
Certificates__ServerRootCACertBase64=<base64-encoded-ca-cert>
```

### Certificate Generation

Certificates are generated by `scripts/create-secrets.sh`:

1. **Global CA**: Creates a root CA for the entire platform
2. **Server PFX**: Generates dual-purpose certificate for HTTPS
3. **SDK Client Cert**: Creates X.500 DN structured certificate for Temporal

```bash
# Generate all certificates
./scripts/create-secrets.sh

# This creates:
# - server/certs/server.pfx (HTTPS server)
# - server/certs/sdk-client.crt (Temporal client)
# - server/certs/sdk-client.key (Temporal client key)
```

## X.500 Distinguished Name Structure

The SDK client certificate uses a specific X.500 DN structure for tenant and user identification:

```
CN=XiansAi, OU=<user_id>, O=<tenant_id>
```

**Components:**
- **CN (Common Name)**: `XiansAi` - Identifies the application
- **OU (Organizational Unit)**: `<user_id>` - User identifier for workflow attribution
- **O (Organization)**: `<tenant_id>` - Tenant identifier for multi-tenancy

**Example:**
```
CN=XiansAi, OU=user123, O=tenant456
```

## .NET Configuration

### HTTPS Server Configuration

```csharp
// In Program.cs or Startup.cs
builder.WebHost.ConfigureKestrel(options =>
{
    options.ConfigureHttpsDefaults(httpsOptions =>
    {
        // Load PFX certificate from base64
        var pfxBytes = Convert.FromBase64String(
            builder.Configuration["Certificates:AppServerPfxBase64"]);
        var pfxPassword = builder.Configuration["Certificates:AppServerPfxPassword"];
        
        httpsOptions.ServerCertificate = new X509Certificate2(pfxBytes, pfxPassword);
    });
});
```

### Temporal Client Configuration

```csharp
// Temporal client configuration with mTLS
var temporalClient = new TemporalClient(
    targetHost: configuration["Temporal:ServerName"],
    clientOptions: new()
    {
        Tls = new TlsOptions
        {
            ServerName = configuration["Temporal:ServerName"],
            ClientCert = new X509Certificate2(
                Convert.FromBase64String(configuration["Temporal:CertificateBase64"]),
                Convert.FromBase64String(configuration["Temporal:PrivateKeyBase64"])),
            ServerRootCACert = new X509Certificate2(
                Convert.FromBase64String(configuration["Certificates:ServerRootCACertBase64"]))
        }
    });
```

## Security Considerations

### Certificate Validation

1. **Server Certificates**: Validated by clients using the platform's CA
2. **Client Certificates**: Validated by Temporal server using the same CA
3. **Mutual Authentication**: Both server and client authenticate each other

### Certificate Lifecycle

- **Generation**: Automated via `create-secrets.sh`
- **Distribution**: Base64 encoded in environment files
- **Rotation**: Regenerate certificates and restart services
- **Validation**: Automatic validation during TLS handshake

## Troubleshooting

### Common Issues

1. **Certificate Not Found**
   ```bash
   # Verify certificates exist
   ls -la server/certs/
   ```

2. **mTLS Handshake Failure**
   ```bash
   # Check Temporal server logs
   docker logs temporal
   
   # Verify client certificate subject
   openssl x509 -in server/certs/sdk-client.crt -text -noout
   ```

3. **Base64 Encoding Issues**
   ```bash
   # Verify environment variables are properly encoded
   echo $Temporal__CertificateBase64 | base64 -d | openssl x509 -text -noout
   ```

### Verification Commands

```bash
# Check certificate details
openssl x509 -in server/certs/sdk-client.crt -text -noout

# Verify certificate chain
openssl verify -CAfile temporal/certs/ca.crt server/certs/sdk-client.crt

# Test Temporal connection
docker exec temporal temporal operator cluster health \
  --address temporal:7233 \
  --tls-cert-path /etc/temporal/certs/temporal.crt \
  --tls-key-path /etc/temporal/certs/temporal.key \
  --tls-ca-path /etc/temporal/certs/ca.crt
```

## Integration with Temporal

### Workflow Attribution

The X.500 DN structure enables:
- **Tenant Isolation**: Workflows are attributed to specific tenants
- **User Tracking**: Workflow execution can be traced to specific users
- **Multi-tenancy**: Support for multiple organizations

### Search Attributes

Custom search attributes leverage the certificate structure:
- `tenantId`: Extracted from `O` (Organization) field
- `userId`: Extracted from `OU` (Organizational Unit) field
- `agent`: Identifies the XiansAI platform
- `systemScoped`: Boolean flag for system-level workflows
